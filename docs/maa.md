# GBFR 自动刷取（Maa 版）使用说明

> [!IMPORTANT]
> **0.3.0 正在开发。** 它有了自己的控制窗口，不再需要 MXU。它也不再自己走菜单选任务：你在任务柜台
> 打开任意任务，软件从那里接手，用游戏自带的“再次挑战”连刷，第 10 次确认时选“是”接着刷。
> 控制窗口还没有在真实游戏里验收过；同一套刷取流程 2026-11-22 经 MXU 在真实游戏里从任务详情页
> 开始，无人操作连刷了 12 轮（跨过第 10 轮弹窗）。目前的验证范围见[限制与证据](#限制与证据)。

本说明为准，[英文版](maa.en.md)是它的翻译。

## 它做什么

它的定位是挂机观看：游戏在前台自己一轮接一轮地打，不追求最快的刷素材效率。

你在任务柜台打开要刷的任务，软件替你接下它并出发。第一轮结算时，软件打开游戏自带的
“再次挑战”，之后游戏自己一轮接一轮地刷。每次结算画面出现，软件计一次数。

游戏每连刷 10 次会弹出“是否继续挑战该任务？”。软件选“是”，游戏不回城，直接开始下一轮，
所以可以一直刷下去。达到次数，或者你选择“本轮后停”时，软件在结算画面关掉再次挑战，
等游戏回到城镇后结束。

战斗交给游戏的完全辅助模式和 AI 队友，软件在战斗中不按任何键。任务失败时，这一轮不计数，
软件确认再次挑战关着后停下，游戏会自己回到城镇。

## 第一次使用前

**在游戏里：**

- 要刷的任务已经解锁，匹配方式用“私人”。任何任务都可以；实测过的是 MANIAC 的
  巨爪岩鳄（“解决沙漠狂徒”），其他任务在[限制与证据](#限制与证据)里说明。
- 开启完全辅助模式（战斗托管模式）。
- 当前的 AI 队伍能稳定通关这个任务。第一次刷某个任务时，请把次数设为 1，先确认一次。
- 游戏语言是简体中文，画面比例 16:9。
- 可选：在加载提示画面按一次 Esc，打开 AUTO SKIP。打开后加载完会自动继续，而且实测在游戏重启后
  仍然开着；不打开也可以，软件会替你按“继续”。

**在电脑上：**

1. 安装窗口要用的 GTK 4、libadwaita 和它们的 Python 绑定。窗口用系统自带的 Python 运行，
   不用另装 Python 包。在 Ubuntu 上（实测 Ubuntu 26.04）：

   ```sh
   sudo apt install python3-gi gir1.2-gtk-4.0 gir1.2-adw-1
   ```

   其他发行版的包名（没有实测）：Debian 同上；Fedora 是 `python3-gobject gtk4 libadwaita`；
   Arch 是 `python-gobject gtk4 libadwaita`。libadwaita 要 1.5 或更新。

2. 构建一个版本目录。需要 Python 3.13 和 `uv`：

   ```sh
   python3 tools/build_maa.py --output dist/gbfr-auto-0.3.0
   ```

   构建会按固定版本下载文字识别模型和后台程序用的 Python 包（其中有 MaaFramework），逐个核对哈希，
   不改动系统和 Steam 设置。已经存在的目录不会被覆盖，所以旧版本可以一直留着用来回滚。
   版本目录建好以后，软件不再往里面写东西；设置、历史和日志放在下面[文件放在哪里](#文件放在哪里)
   说的文件夹里。

3. 把它加进应用菜单：

   ```sh
   dist/gbfr-auto-0.3.0/install.sh
   ```

   这会写入 `~/.local/share/applications/io.github.lowguigui.GbfrAutoLinux.desktop` 和图标，
   并让链接 `~/.local/share/gbfr-auto-linux/current` 指向这个版本目录；菜单项总是通过这个链接
   启动。目录挪动后再运行一次。不加菜单项也可以直接运行版本目录里的
   `./gbfr-control`，但刷完和出错时的桌面通知要有菜单项才会显示：GNOME 只给它认识的程序显示通知。

## 开始刷

1. 通过 Steam 启动游戏，走到任务柜台，打开要刷的任务。停在下面任何一个画面都可以：
   任务详情页（右下角有“承接任务”）、匹配设置、已经接好任务的准备画面、准备完毕的确认面板。
   **游戏启动后，在游戏窗口里点一下。** 每次启动只需要一次，之后窗口在后台也能收到按键。
2. 从应用菜单打开“GBFR 自动刷取”。窗口只会开一个，再点菜单项会把开着的那个叫到前面。
3. 填成功次数（1–999，默认 10），或者打开“一直刷，直到我停止”。
4. 点“开始”。软件自己找到 GBFR 的 Gamescope，不用选设备：它只认运行着 GBFR、通过 Steam 启动的那一个，
   找到零个或多个都不开始。

之后不要操作游戏。窗口会显示从结算画面读到的任务名、“k / N 次成功”和当前阶段；软件因出错停下时，
窗口会写出原因和该怎么做。

## 窗口里有什么

- **状态**：任务名（第一次结算后读到）、成功次数、阶段、本次已用时间（战斗中还显示这一场打了多久）、
  平均每轮用时、任务失败次数，以及停止原因。出错时下面还有一行小字的技术原因。
- **控制**：次数、“一直刷”、开始、本轮后停、立即停止。会话进行时次数不能改。
- **最近几次会话**：最近 5 次会话各一行，写着结束时间、任务名、结果、次数、平均每轮用时和总用时。
- **打开日志文件夹**：打开 MaaFramework 的日志所在的文件夹。
- 右上角菜单里的“显示的信息…”可以逐项打开或隐藏上面这些信息，改了立即保存。“最近几条日志”
  默认隐藏，其余默认显示；控制部分总是显示。
- 标题栏上的图钉打开 GNOME 自己的窗口菜单（和在标题栏上点右键一样）。在里面选“置顶”，窗口就
  一直留在别的窗口上面，再选一次取消。图钉不显示是否已经置顶，因为 GNOME 不让程序读取这个状态。
- 刷完或出错停下时，桌面会弹一条通知；你自己点停止时不弹，点“开始”后马上被拒绝（比如游戏没开）
  也不弹，因为窗口上已经写着原因。
- 会话进行时，软件阻止屏幕变暗、熄灭和锁屏，会话结束或后台程序退出时撤掉。这只在 GNOME 上有效，
  不改电源和锁屏设置；做不到时窗口会说一句，刷取照常进行。

窗口用系统的 Python 运行，每次会话另起一个后台程序（运行器），由它加载 MaaFramework、截图和按键。
窗口关掉或意外退出时，后台程序会自己停下；后台程序意外退出时，窗口会说明，并对用到的按键各发一次松开。

## 一轮是怎么跑的

| 阶段 | 软件做什么 |
|---|---|
| 第一轮 | 在任务详情页接任务，确认私人匹配，准备完毕后出发 |
| 战斗 | 只看不按。一轮战斗超过 30 分钟就停下（游戏自己的任务时限通常更早结束这一轮） |
| 结算 | 结算画面出现时计一次数。到了奖励页：要继续，就打开“再次挑战”；要停，就关掉它。软件等奖励展示完再按 3，按完读回开关状态，没变就再按一次 |
| 之后每轮 | 游戏自己开始下一轮。再次挑战开着时，游戏会跳过宝箱阶段 |
| 第 10、20…轮 | 游戏把再次挑战重置为关，并弹出“是否继续挑战该任务？”，光标在“否”上。要继续时，软件按上方向键，在新截图上确认光标到了“是”，再按回车。游戏随即重新打开再次挑战，不回城。要停时，软件不回答，等它超时回城 |
| 任务失败 | 游戏显示 QUEST FAILED，然后只有一页没有完成奖励的结算页。软件不计数；如果再次挑战开着，先按 3 关掉它（否则游戏会重试），然后停下。游戏 30 秒后自己回城 |

实测（2026-11-22，巨爪岩鳄，测试队伍）：开着再次挑战时每轮约 6 分钟，其中战斗约 5 分钟；
结算到下一轮开战约 70 秒，第 10 轮选“是”之后也一样。

## 停止

- **达到次数**：自动停下，游戏回到城镇后结束。
- **本轮后停**：点“本轮后停”。软件在当前这一轮的结算画面关掉再次挑战，游戏回城后结束。
- **立即停止**：点“立即停止”。它只停止软件的按键，游戏不会暂停。如果再次挑战开着，
  游戏会自己继续刷，最多刷到下一次第 10 轮的弹窗，然后回城。想马上停，请在结算的奖励页按 3，
  关掉再次挑战。窗口会显示“已按你的要求停止”和已计数的次数，并说明再次挑战是否还开着。
- **刷本时关窗口**：窗口会先问。选“停止并关闭”等于立即停止，后台程序停下后窗口关闭；选“取消”什么都不变。
- **后台程序没按时停下**：请求停止 35 秒后后台程序还没退出，窗口会问要不要“结束后台”。
  它只结束本软件的后台程序，不碰游戏，然后对用到的按键各发一次松开。
- **退出游戏**：用游戏自己的菜单退出。不要强行结束游戏、Wine/Proton 或 Gamescope 进程，
  那样可能损坏存档。

## 出错时

软件因出错停下时，窗口会写出原因和该怎么做，下面一行小字是技术原因。常见情况：

| 窗口上说 | 怎么办 |
|---|---|
| 没有找到正在运行的游戏 | 通过 Steam 启动游戏，等画面稳定后再开始 |
| 找到了几个运行着 GBFR 的 Gamescope | 只保留一个游戏在运行 |
| 已经有一个刷取在运行 | 可能是 MXU 版本目录里的那个，或者另一个窗口。先停掉它，再开始 |
| 画面在限定时间内没有变成预期的样子 | 看一眼游戏，打开要刷的任务（详情页或准备画面）再开始。常见原因：起点不对、已经接了别的任务、有弹窗、游戏语言不是简体中文、游戏启动后没点过窗口 |
| 游戏或它的 Gamescope 重启过或者关闭了 | 通过 Steam 重新启动游戏，等画面稳定、在窗口里点一下，再打开任务重新开始。已计数的次数有效 |
| 任务失败 | 这一轮不计数，游戏会自己回城。换更强的队伍或更低的难度，先用 1 次确认能通关 |
| 第 10 次的确认弹窗里没能选上“是”；会话还没结束游戏就回到了城镇 | 已计数的次数有效。在柜台重新打开任务再开始 |
| 战斗超过了 1800 秒上限 | 确认完全辅助模式开着，队伍能通关 |
| 按了两次 3，“再次挑战”仍然没有打开 | 看游戏是否卡住；在柜台重新打开任务再开始 |
| 游戏画面里有别的窗口或覆盖层；检测到 Ctrl、Shift、Alt 之类的键按着 | 关掉覆盖层、松开按键，再重新开始 |
| 资源或 OCR 模型加载失败 | 重新构建版本目录 |
| 后台程序意外退出了 | 窗口已经对用到的按键各发了一次松开；看一眼游戏画面。日志文件夹旁边的 `window-runner.log` 和那次会话的日志可以帮助查原因 |

游戏启动后如果没在窗口里点过，按键可能完全不生效，结果通常是“画面在限定时间内没有变成预期的样子”。
点一下游戏窗口再开始。

## 文件放在哪里

| 内容 | 位置 |
|---|---|
| 设置：次数、显示哪些信息、窗口大小 | `~/.config/gbfr-auto-linux/settings.json` |
| 会话历史，每次会话一行 | `~/.local/state/gbfr-auto-linux/history.jsonl` |
| MaaFramework 的日志，每次会话一个文件夹，只留最近 5 次（刷 1 小时约 190 MB） | `~/.local/state/gbfr-auto-linux/logs/` |
| 后台程序最近一次会话的错误输出 | `~/.local/state/gbfr-auto-linux/window-runner.log` |
| 当前会话的状态 | `$XDG_RUNTIME_DIR/gbfr-auto-linux/session.json` |

这些文件新旧版本共用，删掉也不影响版本目录。`uninstall.sh` 不动它们。

**内存。** 会话进行时，MaaFramework 的原生内存每小时大约涨 130 MB（2026-11-22 测量），会话结束、
后台程序退出时全部释放。连续刷几个小时会多占几百 MB；这是已知现象，目前接受。

**Python。** 版本目录里的 `.venv` 用的是 uv 管理的 Python 3.13（在 `~/.local/share/uv/python/` 下）。
用 `uv python uninstall` 删掉它，所有版本目录的后台程序都会启动不了；重新构建即可。

## 更新与回滚

1. 把新版本构建到一个新目录，旧目录不要动。
2. 停掉正在跑的会话，关掉窗口。
3. 运行新目录里的 `./install.sh`。链接从此指向新目录，菜单项本身不变。

回滚就是运行旧目录里的 `./install.sh`。0.3.0 开发版里较早的版本目录（`install.sh` 里没有 `current`
链接的那些）把自己的路径直接写进菜单项，而 GNOME 的应用列表在菜单项消失过一次之前会一直启动原来的
路径：要回到这样的目录，先运行当前目录里的 `./uninstall.sh`，等一分钟，再运行旧目录里的 `./install.sh`。
带 MXU 的旧版本目录（0.2.0，以及 0.3.0 开发版里有 `mxu` 文件的那些）照旧用它自己的 `./start.sh`；
两边共用会话锁，不会同时控制游戏。控制窗口通过真实游戏验收之前，`tools/build_maa.py --mxu` 还能构建
MXU 版。`./uninstall.sh` 删除菜单项、图标和链接，但只在链接指向它所在的目录（或者指向的目录已经
不在了）时才删。不要在会话运行时更新任何部分。

## 限制与证据

**支持范围。** MaaFramework 5.16.1（Python 包，自带原生库），Linux x86-64，GNOME 桌面：窗口和通知在别的
桌面上也许能用，但没有测过，防止熄屏只在 GNOME 上有效。窗口需要系统的 Python 和 GTK 4、libadwaita 1.5
或更新；测试用的是 Ubuntu 26.04 的 GTK 4.22.4 和 libadwaita 1.9.1。游戏 2.0.6，简体中文，16:9，
识别时缩放到 1280×720。截图走 Gamescope 的 PipeWire 输出，输入走它的 libei 接口；需要 Gamescope 3.16.22
或更新（3.16.20 的 PipeWire 截图会卡住）。一次只控制一个游戏、一个会话，第二个控制者会被拒绝。
只支持私人任务。

**已经验证的：**

- 游戏自身的行为（2026-11-22，在不显示到桌面、不出声的 Gamescope 里，用测量脚本跑巨爪岩鳄）：
  - 第 10 轮弹窗：按上方向键、再按回车选“是”后，同一页的开关变成“撤销再次挑战”，倒计时结束后
    直接开始第 11 轮，没有回城；第 11、12 轮没有再弹窗。
  - 任务失败（撤掉 AI 队友单刷）：QUEST FAILED 之后只有一页结算，0 卢比、“无奖励道具”，
    不按键也会在 30 秒后回城。
  - 战斗中一直按住 W 没有让这一副本的战斗变快（6 轮对 5 轮，平均 308 秒对 299 秒）。
  - 加载画面的 AUTO SKIP 在游戏重启后仍然开着。
- 后台程序（运行器）的真实游戏检查（2026-11-22，从命令行运行，不经 MXU，游戏用平常的窗口模式）：
  从巨爪岩鳄的任务详情页跑 3 轮，读到了任务名；再跑一次并在第 2 轮战斗中请求本轮后停止，
  完成 2 轮后回到城镇。每次会话结束后没有键按着，防熄屏只在会话进行时登记。
- 控制窗口（2026-11-23，在私有的无头 GNOME Shell 里，后台程序换成脚本化游戏）：跑完 3 次、
  第 2 轮战斗中本轮后停（只完成 2 次）、立即停止、后台程序意外退出和不肯停下时的松键、
  关窗口的确认、显示设置、只开一个窗口、刷完时的桌面通知；构建出的版本目录在没有游戏时点开始，
  提示先启动游戏；从安装的菜单项能打开窗口。
- 0.3.0 开发版的真实游戏检查（2026-11-22，经 MXU 运行，游戏在不显示到桌面、不出声的 Gamescope
  里）：停在巨爪岩鳄的任务详情页开始，设 12 轮，无人操作跑完。软件只按了预期的 8 个键：开局 4 个，
  第 1 轮结算时打开再次挑战，第 10 轮弹窗上的上方向键和回车，第 12 轮结算时关掉再次挑战。
  选“是”之后第 11 轮在 72 秒后开始，没有回城，和其他轮的间隔一样。最后停在城镇；控制面板读到了
  任务名“解决沙漠狂徒”，MXU 的日志显示了每次计数和结束提示。
- 0.2.0-rc.1 的真实游戏验收（2026-11-22，经 MXU 运行，游戏窗口在后台）：巨爪岩鳄连续 12 轮
  无人操作（那一版在第 10 轮让弹窗超时，回城后重新接任务）；第 2 轮战斗中请求本轮后停止；
  第 1 轮战斗中立即停止。MXU 的日志显示了每次计数和结束提示；第二个控制者被拒绝。
- 0.3.0 的离线测试：按实测行为编写的脚本化游戏场景，包括第 10 轮选“是”、一直刷时连续三次选“是”、
  光标移不到“是”、弹窗没回答就回城、失败时再次挑战开着和关着、失败页在计数时才认出来；
  19 张实测截图的识别用例（只保留识别区域），包括失败页、光标在“是”和“否”上的弹窗；
  用新的识别把当天失败那一局和 12 轮的录像逐张重放。

**还没有验证的：** 控制窗口还没有在真实游戏里跑过，也没有在真实桌面上打开过：缩放、图标、
通知和防熄屏的效果要在真实桌面上看。0.3.0 在真实游戏里只从任务详情页开始跑过，从匹配设置、准备画面
和确认面板开始只用实测截图检查过识别。这一版没有在真实游戏里重跑立即停止和拒绝第二个控制者，
也没有遇到真实的失败（失败的处理只在脚本化游戏里测过）。只实测过巨爪岩鳄：其他任务的战斗画面、
目标文字和时长没有看过。第 20 轮的弹窗、选“否”的效果、失败后按 3 重试会怎样都没有测过。
按键前的检查在真实游戏里拦下一个被按住的键，也还没有见过。

**不做的事：** 自动启动游戏、从标题画面继续、走到柜台选任务、配装、消耗素材、推进剧情、
战斗中的输入；其他语言、分辨率和画面比例。完全辅助模式和 AI 队友能否通关，取决于你的队伍。
有用的成长目标和已经验证的任务有什么区别，见[成长范围](progression.md)。

## 开发

- 任务、文案和验证过的任务在 `assets/catalog.json`；`tools/maa_catalog.py` 由它生成
  `assets/interface.json`。
- 识别和流程在 `assets/resource/pipeline/farming.json`：`GBFR_See_*` 是“看到了什么”，
  动作节点把它们和 Agent 的 `GBFRSession` 判断组合起来。没有任何识别依赖任务名。
- `maa_agent.py` 负责计数和停止判断，`maa_session.py` 是计数规则，`maa_guard.py` 做目标和按键检查，
  `maa_messages.py` 把停止原因翻译成上面那些中文提示。
- `control_window.py` 是窗口，`control_view.py` 是它显示什么、按钮什么时候能点的规则（不依赖 GTK，
  在 CI 里测）。每次会话，窗口启动一个 `maa_runner.py` 子进程，经 `maa_protocol.py` 的 JSON 行协议
  对话；命令行用法见 [tools/README.md](../tools/README.md)。
- 版本目录里的启动、安装和卸载脚本在 `assets/bundle/`，图标在 `assets/icons/`。

健康检查：

```sh
.venv/bin/pytest
.venv/bin/ruff check .
.venv/bin/reuse lint
```

识别用例需要 OCR 模型：把 `GBFR_MAA_OCR_MODEL` 指向一个 `model` 目录，或者先用
`python3 tools/build_maa.py --ocr-only --output <目录>` 下载。`tools/maa_replay.py` 在截图上
离线跑识别，`tools/maa_fixtures.py` 把一张截图处理成可提交的用例。窗口的冒烟测试
`tests/window_smoke.py` 只在本地跑：它会打开窗口、自己点按钮，要在一个私有的桌面会话里运行。
测试的覆盖范围见[测试说明](../tests/README.md)。
